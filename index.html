AIMotion Sales Agent 产品架构

从现实汽车销售业务出发，在 SCRM 中持续经营 Customer / Opportunity，并在每次任务、渠道与业务条件下完成销售判断、推进、执行和客户沟通。

01 · Sales Agent 产品架构总览

以 Customer / Opportunity 为长期经营对象，把一次互动变成持续经营

SCRM 管理的是长期存在的 Customer 及其当前 Opportunity；一次私信、表单、外呼或人工跟进只是其中一次 Session / Touchpoint。

2.2 客户购车状态

SCRM 持续维护意向车型、用车场景、预算、购车时间、必选条件、付款偏好、决策因素、当前卡点、购车阶段和决策人等购车状态；
Agent 按当前问题读取，并随新信息和业务结果持续更新。

业务边界：客户购车状态属于 SCRM 中的客户 / 商机持续状态，不单独形成新的销售业务域。

2.3 十二类一级销售业务

业务域核心业务问题

客户不会按 12 个业务域顺序推进；一次购车事项可同时涉及多个业务域，并随新信息在业务域之间切换。

业务范围从经销商实际销售流程、客户购车旅程和数字零售能力三个视角交叉校验，参考 NADA、KPMG 和 CDK Global；这些框架用于检查业务范围完整性，不替代 AIMotion 自己的业务结构。

03 · 业务信息、现实来源与 AIMotion 支持方式

区分 AIMotion 已有支持与需要现实业务方确认的结果

AIMotion 内部已有支持

  • 后台数据 / 配置：车型库、Dealer 信息、价格、Promotion、Finance 产品等。
  • SCRM：Customer / Opportunity、历史、客户购车状态和已有业务结果。
  • Market Knowledge / Skill：不同 Market 稳定的业务机制、概念、规则和计算口径。
  • Sales Node / Node Relation：根据输入形成业务结果，并复用其他节点结果。
  • 业务判断 / 计算 / 预估：匹配、比较、月供、付款方案、估值参考等派生结果。

现实业务系统和数据来源

  • DMS 及 Dealer 业务系统：库存、车辆、Deal / Order、合同和部分交易 / 交付状态。
  • OEM 系统：车型、订单、车辆分配、部分库存和生产 / 在途状态。
  • 银行 / 金融机构系统：Finance 产品、审批、借贷结果、Funding。
  • 政府 / 授权机构：权属、车辆风险、注册 / 上牌等正式状态。
  • 第三方专业数据平台：车辆历史、市场价格、估值和车型信息。
  • 专业媒体 / 测评 / 公开内容：车型测评、安全、市场评价和社媒内容。
  • 真人 / 专业团队：没有可靠系统结果，或最终结果需要人工商业判断时确认。

DMS（Dealer Management System，经销商管理系统）代表 Dealer 常见的核心业务系统。不同 Dealer 的系统结构并不完全一致，因此后文使用“DMS / Dealer 业务系统”表示这类现实数据来源，不假设所有 Dealer 都把全部数据放在同一套 DMS 中。

跨 Market 的复用方式

D1–D12 的业务信息类型保持相对稳定；不同 Market 主要改变具体业务规则、数据来源和计算口径。当地机制优先挂在已有业务信息下。只有出现新的、稳定且现有结构无法承载的信息类型时，才需要调整通用结构。

05 · 销售任务与触达渠道

Task / Trigger 定义为什么启动，Channel 定义如何交互

5.1 Task / Trigger｜任务 / 触发

Task 决定当前互动的业务目标、推进重点和结束条件。

任务当前主要目标

不同 Task 可以处理相同的 Sales Domain，但阶段目标会不同。例如同样是 Finance 问题，被动回复重点是解决客户当前疑问；线索清洗还可能承担指定画像或状态采集；激活唤醒则首先需要恢复有效互动。

5.2 Channel｜触达渠道

当前及未来 Channel 可以包括公域私信、WhatsApp、Voice Call / Outbound Call，以及其他可接入渠道。Channel 主要影响互动形式、沟通节奏、表达方式、渠道合规要求，以及该渠道下实际可使用的能力。

同一个 Channel 可以承载不同 Task。例如 Voice 可以用于线索清洗、激活唤醒、销售跟进；进入车主经营阶段后，也可以承载保养提醒等新的 Task。新增 Voice 或其他渠道时，不需要重新定义汽车销售业务本身，而是在对应 Task 和业务条件下明确渠道差异。

06 · 业务场景组合｜Scene

Scene 描述这一次 Sales Agent 所处的业务运行条件

Task / Trigger｜任务 / 触发为什么这次 Agent 被启动、当前阶段要完成什么
×
Sales Domain｜销售业务域当前正在处理哪一类汽车销售问题
×
Business Context｜业务上下文Market、New / Used、Channel、Dealer / OEM 配置等当前运行条件

Task 在 Scene 中单独作为一个维度；Channel 与 Market、New / Used、Dealer 等共同构成 Business Context。

6.1 Scene 示例

  • 被动回复 × Trade-in × AUS Used Car
  • 线索清洗 × Finance × MX New Car
  • 激活唤醒 × Affordability × MY Private

一个 Scene 用于明确这次任务的目标、当前处理的销售问题、Market / New-Used / Channel / Dealer 条件，以及哪些已有知识、数据、策略和执行能力需要在这组条件下生效。

6.2 新需求如何进入现有架构

新需求类型架构中的处理方式

新增 Market、Task 或 Channel 时，可以继续组合已有业务结构，再判断哪些数据、知识、策略或执行方式需要针对新 Context 调整，而不需要重新建立一套独立 Sales Agent。

6.3 Scene 完整性怎么理解

Scene Model 的完整性主要体现在：新增业务需求能够被稳定归类到 Task、Sales Domain 和 Business Context 三个维度中，并沿现有结构扩展。这解决的是结构完整性和可扩展性。

各 Market 当前已经实现了多少 Task × Domain × Context 组合，需要单独通过 Coverage Map 盘点；现有材料不足以据此宣称所有组合已经实现。

内容优先级和回复结构

Final Reply Generation / Localization

最后才进入最终回复生成和本地化表达。本轮回复规划负责形成最终业务决策，而不只是最终语言润色。

例如在线索清洗中，系统已经知道“当前没有 Promotion”，但客户本轮没有询问 Promotion，且当前 Cleaning Goal 更关注购车时间或到店推进，那么沟通策略可以决定这一事实是否需要主动表达。

固定规则：Task、Market 或沟通策略可以影响本轮主动表达什么、重点放在哪里，但不能遗漏客户已经明确提出且尚未解决的问题。

业务资产告诉 Agent 什么主要服务于

例如，“澳洲 Finance 通常存在某种产品机制”属于 Market Knowledge；“当前 Dealer 实际配置了什么 Finance 产品”属于当前业务事实。两者会共同参与判断，但承担不同职责。

业务事实口径：用于约束 AIMotion 自己的数据语义，例如 Dealer Listing 能支持哪一级库存结论；Promotion 配置代表公开 Promotion 还是客户级个性化 Offer；Finance 字段能支持基础信息，还是客户级正式 Finance Result。它不创造新的业务事实，只保证 Agent 正确理解已经进入系统的信息。

10 · Skill 的模块化封装与按需加载

Skill 是一组可以按需加载的业务资产包

查看四项封装条件的完整判断
封装条件判断含义
有稳定的业务 Owner这组内容有明确、长期稳定的职责。
内部内容高度相关适合一起维护，而不是把互不相关的规则强行打包。
能够跨多个 Scene 复用不是只服务某一个最终 Case。
独立按需加载有价值能减少无关 Context，或者明显提升维护、扩展效率。

当前自然的模块化资产

Market Static Knowledge｜市场静态知识

承载某个 Market 稳定的汽车销售机制、概念和行业知识，例如当地价格定义、Finance 机制、Trade-in 规则，可被多个 Sales Domain 复用。

AIMotion Fact Semantics｜AIMotion 业务事实口径

承载 AIMotion 后台字段、配置、Tool 和系统结果的业务语义，使多个业务问题共用同一套数据解释规则。

Communication / Reply Rules｜沟通与回复规则

影响本轮内容选择和推进方向的部分参与本轮回复规划；纯语言、本地化和最终表达要求用于最后的 Reply Generation。

当前 Finance 可以由 Finance 相关节点和关系、Market Knowledge、事实口径、Sales Strategy 以及 Finance 执行边界共同完成，因此 Finance Domain 本身不自动对应 Finance Skill。如果未来 Finance 形成独立、复杂且可复用的专业处理方法，再根据实际复杂度模块化。

11 · Tool、系统执行与人工协作

根据客户真正需要的结果，选择能够可靠形成该结果的执行方式

例如客户只是询问 Finance 产品机制时，Agent 可以直接基于已有配置和 Knowledge 回答；客户需要个人实际审批结果时，则由 Finance Team 或对应金融业务方形成结果。

现有 AUS 边界设计也采用这一方向：Handoff 按客户需要的业务结果决定，而不是只看到 Finance、Trade-in、Inventory 等 Topic 就统一转给某个 Team。

12 · Agent 运行时｜Harness 与 Agent Loop

Harness 组织运行环境，Agent Loop 持续处理新信息

例如一个 Finance 结果返回后，需要更新受它影响的付款方案；已经成立且没有受到影响的车辆事实和客户条件继续保留，不需要整轮从头重算。
